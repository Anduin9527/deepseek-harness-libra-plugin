# DeepSeek Harness Libra bundle 集成补全计划（2026-08-24）

## 文档职责

本文解决 `@libra-tools/dsh-bundle` 当前只完成内部 facade、尚未完成真实 DeepSeek Harness 生命周期接入，以及 TypeScript 与 Libra Agent Bridge 实际协议存在偏差的问题，目标是交付可复现、可审查、可回滚的桥接 bundle。

本文定义任务和验收边界。代码落地后，任务状态必须以本文件的实现状态附录和最新
evidence 为准；外部 DSH/真实 Libra 门未通过时不得宣称整体发布完成。

### 适用范围

- `packages/protocol`、`packages/bridge-client`、`packages/session`、`packages/tools`、`packages/workspace`、`packages/context`、`packages/ui`、`packages/bundle`。
- DSH profile/plugin 注册、session/agent/subagent 生命周期、context injection、UI card/action 和真实 Libra bridge contract flow。
- 协议 fixture、集成测试、构建/打包、版本、release evidence 和兼容文档。

### 非目标

- 不在本计划内修改 Libra Rust Agent Bridge；Libra Rust 实现由 `DEP-LB-02` 作为协议权威。
- 不在本计划内升级 DeepSeek Harness；只适配固定 revision `dsh-v0.1.0-rc.7`。
- 不实现新的 Libra method、Rust 错误码或新的 Git 语义；发现 authority 缺口时创建 `FIX-*` 或转交 Libra 计划。
- 不把旧的 `docs/release-evidence-REL-TS-01.md` 直接当作当前完成证据；它只作为历史线索。

### 成功定义

- TypeScript 请求、响应、workspace lease、approval、checkpoint 和 context 结构与固定 Libra authority receipt 一致，并对未知/越界输入 fail-closed。
- bundle 能在固定 DSH revision 中注册并真正接收 Harness session/event、agent injection、compaction、UI action 和 dispose 生命周期。
- 真实流程 `initialize → session.open → event.append → ack/replay → checkpoint/evidence → close` 有可复现测试和脱敏证据。
- 所有非延后任务达到 `Lifecycle=done` 且 `Acceptance=complete`，最终 Claude review 明确返回 `PASS`，并完成一次独立发布切片 `REL-TS-02`。

## 已决议设计决策

### ADR-TS-01: Libra Rust source 与 handoff receipt 是协议唯一权威

- **Status:** Accepted
- **Context:** 当前 JSON fixture 的版本、origin 和 SHA 与实际 Libra checkout 不能建立可复现绑定。
- **Decision:** TypeScript 只消费由 `DEP-LB-02` 提供的固定 source revision、golden frame、method/limit/error 摘要和 SHA256 receipt；不得根据旧 fixture 自行扩展协议。
- **Alternatives considered:** 继续维护 TypeScript 独立 schema 被拒绝，因为会产生第二个 schema source；直接修改 Libra Rust 被拒绝，因为超出本仓库范围。
- **Consequences:** authority receipt 未到达前相关任务最多为 `remote-pending`，不得标记 complete。
- **Revisit when:** Libra bridge 发布新的 protocol major 或 handoff 格式变化时。

### ADR-TS-02: Harness 适配集中在 bundle boundary

- **Status:** Accepted
- **Context:** 现有各 package 是可测试的 domain facade，但没有宿主生命周期接线。
- **Decision:** 由 `packages/bundle` 提供唯一 Harness adapter，负责注册 session/event/context/UI hooks、注入 runtime 和统一 dispose；底层 package 不直接依赖 DSH 全局对象。
- **Alternatives considered:** 每个 package 直接调用 Harness API 被拒绝，因为会产生生命周期重复注册和难以回滚的全局状态。
- **Consequences:** TS-06 是后续 context/UI 任务的集成前置；adapter 必须使用 capability detection 和 fail-closed fallback。
- **Revisit when:** DSH 提供稳定的官方 typed integration SDK，且能替换当前 boundary adapter。

### ADR-TS-03: 单一 family release point

- **Status:** Accepted
- **Context:** bridge、session、tools、workspace、context、UI 必须一起经过真实 contract flow 才能形成可用 bundle。
- **Decision:** TS-01..TS-09 登记为 `REL-TS-02` 的 family child，由唯一 release point 完成 package patch bump、lockfile/tool-generated refresh、build、pack、commit、push 和发布证据。
- **Alternatives considered:** 每个内部 package 独立 npm 发布被拒绝，因为公开交付面只有 `@libra-tools/dsh-bundle`；旧 `batch-release child` 被 v2.1 ER-08 废止。
- **Consequences:** family child 不单独 bump，但必须通过自己的 A/B 门并继承 release point 的 C/D 覆盖；发布必须串行。
- **Revisit when:** 内部 package 转为独立公开 npm surface 时。

## 全局工程约束

- **GC-01 现状核实:** 每卡开工前刷新源码、测试、DSH revision 和 Libra receipt；已实现内容转为补测/补文档，不重复实现。
- **GC-02 单一事实源:** protocol、method schema、error mapping、approval policy、config allowlist 和 lifecycle registration 各有唯一实现源。
- **GC-03 fail-closed:** 未满足 protocol major、scope、approval、path、secret redaction 或 schema validation 时拒绝请求，不静默降级为成功。
- **GC-04 原子状态:** outbox、ack、operation id、lease fence、staging artifact 和 dispose 必须定义原子边界、幂等规则和崩溃恢复。
- **GC-05 字节预算:** frame、event、batch、result、outbox 和 context 的容量全部按 `Buffer.byteLength(value, "utf8")` 计算。
- **GC-06 生命周期隔离:** bundle 负责注册/注销 Harness listeners、timers、child process 和临时目录；重复初始化和重复 dispose 必须幂等。
- **GC-07 DSH 兼容:** 只支持 `dsh-v0.1.0-rc.7@99f6f02fecdb7dff40c3fbc9470f5907c29f74ca`，升级必须新建 compatibility decision 和验证矩阵。
- **GC-08 证据脱敏:** review、integration、release log 禁止记录 token、secret、PII、原始敏感 payload 和不可复现私有绝对路径。
- **GC-09 TypeScript 质量:** 生产代码不新增未解释的 `any`、空 catch、无界 Map/数组或未清理 listener；异常必须映射到稳定可测试状态。
- **GC-10 精确写集:** 不清理用户已有改动；提交时只纳入本任务写集和计划中声明的 release 文件。
- **GC-11 安全与供应链:** 本地 stdio bridge 不引入网络认证；child 只接收 allowlist env；outbox 文件使用 owner-only 权限；npm 发布使用短期凭据/OIDC（若可用）、lockfile、tarball allowlist 和 provenance，禁止把长期 token 放入仓库或日志。

## 任务卡粒度规则

- **G-01 单一行为轴:** 每卡只承载一个可独立恢复的行为轴和一个恢复模式；协议、存储、Harness 生命周期、UI 和发布不得隐式合并。
- **G-02 同轴闭合:** 同一行为轴的实现、测试、文档和兼容同步必须在同卡内闭合，不拆成“只补测试”碎片卡。
- **G-03 条目上限:** implementation 卡的 AC/Verification 各不超过 8 条，release 卡各不超过 12 条；强制全局门不计入卡内上限。
- **G-04 规模上限:** 默认只允许 S/M；需要 L 的不可拆机械变更才可另行登记白名单 waiver；本计划无 waiver。
- **G-05 自包含:** 卡内必须写清输入、产物、exact verification、失败路径和文件落点，不依赖另一张卡正文中的未交付约定。
- **G-06 具体依赖:** Dependencies 只能引用具体 Task/DEP ID，不使用“Phase 完成”“前置工作”或范围缩写作为悬空依赖。
- **G-07 默认发布切片:** 默认每个可发布行为轴独立切片；只有明确登记为 family 的强耦合 bundle 才共享发布点。
- **G-08 family 规则:** family child 不 bump、不发布，只继承指定 family release point 的 C/D 覆盖；release point 必须唯一且位于所有 child 之后。
- **G-09 拆分闭环:** 每次拆分/合并都必须同步修订历史、DAG、REL、追溯、测试矩阵和里程碑。
- **G-10 写集并发:** implementation write set 相交只能串行或合并；release write set 统一串行，不作为实现阶段并发依据。
- **G-11 任务类型:** 每卡必须明确 implementation、release 或其它模板允许的 Task type，并采用对应的 scope、AC/VER 和 C/D 规则。

## 执行检查必备需求

- **ER-01 工作区检查:** 开工前执行 `git status --short --branch`，确认分支、脏状态和目标写集；已有用户改动不得覆盖。
- **ER-02 authority 核对:** 开工前记录 Libra source revision、golden frame SHA、DSH revision、fixture SHA 和 package version。
- **ER-03 粒度门禁:** 每卡开工前核对 `Granularity` 行；出现第二行为轴、AC/VER 超限、scope 变为 L 或写集冲突时先拆卡。
- **ER-04 验收门:** 每卡必须通过 A focused test、B 类型门和 family release point 的 C 全量门；有真实外部环境依赖时先 `remote-pending`。
- **ER-05 Claude review:** 计划和实现的 review issue 必须修复并重跑相关验证；最终计划必须有明确 `PASS`，P0/P1 不得残留。
- **ER-06 文档兼容:** package export、protocol、config、error、profile 或公开 action 变化必须同步 README、protocol docs、CHANGELOG 和 compatibility matrix。
- **ER-07 安全守卫:** 测试必须覆盖 env allowlist、路径穿越、redaction failure、scope mismatch、approval deny、stale fence 和错误 source。
- **ER-08 TS release:** `REL-TS-02` 负责公开 `packages/bundle/package.json` version、`pnpm-lock.yaml`、publish manifest、协议 fixture/receipt、CHANGELOG 五个发布面；根 workspace `package.json` 和内部 `0.0.0` package version 不是独立发布面。lockfile 只能由 pnpm/tool 生成，提交后用 `gh` 触发仓库 release workflow（若本仓库没有 workflow，则记录 N/A 和实际 npm 发布命令）。
- **ER-09 证据完整:** 每个完成卡记录 exact command、结果、环境版本和脱敏 artifact；浮动 `npx`、旧绝对路径和无 SHA 证据不可接受。

### 安全、认证与供应链闭合

- **身份模型:** 插件只信任由本地 Libra child process 和 trusted bridge session 派生的 source/session/workspace identity；模型输入不能设置 actor、owner、repository root、fence 或 executable。
- **传输模型:** bridge 使用本机 stdio，不监听网络端口；stdio frame 按 protocol limits 校验，stderr 永不进入 JSON-RPC stdout。
- **存储模型:** outbox、quarantine、staging 和 evidence 目录必须 root-contained、owner-only，并在写入前做权限/路径检查；本计划不保存长期 secret。由于数据只落在本机受控目录，应用层 at-rest encryption 不在本计划范围，依靠 filesystem permissions，并在部署到共享/远端存储时阻止运行。
- **加密边界:** 本地 stdio 不提供网络加密，且不暴露网络端口；若未来 bridge 改为网络 transport，必须新建安全 ADR，补 TLS、peer authentication 和 key rotation，不能在本计划内静默切换。
- **凭据模型:** DSH/Libra binary 路径、revision 和 profile 通过显式环境或参数传入；npm 发布只使用短期 CI credential/OIDC 或用户明确提供的临时 token，日志只记录 credential-free receipt。
- **供应链模型:** `pnpm-lock.yaml`、pinned DSH artifact、Libra binary SHA、package tarball allowlist、provenance 和发布版本必须相互可追溯；任一 SHA/manifest 不一致立即阻止 release。
