# DeepSeek Harness Libra TypeScript 插件计划（2026-08-18）

## 文档职责

本文规划 DeepSeek Harness 侧 Libra TypeScript 插件的实现，目标是交付一个可独立安装的
`@libra/dsh-bundle`，通过 `libra agent bridge --stdio` 的 JSON-RPC NDJSON 协议，把
Harness 的 session、workspace、checkpoint、evidence、provenance 和高层工具能力接入
Libra。

本文只规划 TypeScript 项目；Libra Rust bridge、Agent ingress、SQLite/对象存储、workspace
lease 的权威实现由 Libra 仓库另行承接。

### 适用范围

- TypeScript monorepo、协议 schema、bridge client 和运行时校验。
- Harness session/event 投影、outbox、幂等、断点续传和隐私脱敏。
- 高层 Libra tools facade、workspace/subagent 绑定、context 注入、profile/bundle 和 UI 卡片。
- 插件单元测试、bridge contract test、Harness 集成测试、文档和 npm 发布产物。

### 非目标

- 不在本仓库实现 `libra agent bridge --stdio` 的 Rust 服务端。
- 不直接打开或写入 `.libra/libra.db`、`.libra/objects` 或 Libra SQLite 表。
- 不重新实现 DeepSeek Harness Agent loop、session persistence 或模型 provider。
- 不把 MCP 或其它旧工具服务器传输作为标准写入协议。
- 不替代 `libra code --control stdio`；后者只负责控制 Libra 自己运行中的 Agent session。
- 不在第一版实现 cloud backup、publish、危险 VCS 操作或完整 transcript raw export。

### 成功定义

- `@libra/dsh-bundle` 可由 `dsh plugin --profile libra` 安装并通过 `dsh --profile libra --dump-config` 验证组合结果。
- 插件能启动 `libra agent bridge --stdio`，完成协议协商、session open/close 和结构化错误处理。
- Harness session/event 能经 outbox 批量写入 Libra，重复事件不会重复落库，进程重启后可以继续同步。
- 高层工具只调用 typed bridge 方法，模型无法构造任意 shell 或数据库请求。
- workspace、subagent、checkpoint、evidence 和 commit 关联可查询，且 actor 身份不可由模型伪造。
- `pnpm lint`、`pnpm typecheck`、`pnpm test`、bridge contract test 和 Harness 集成测试通过。
- 文档、协议 schema、变更日志和 npm package metadata 与实际行为同步。

### 跨仓库契约与依赖方向

两份计划使用带仓库前缀的依赖编号，避免把同名本地依赖编号误读成双向依赖：

- `DEP-LB-01` 只表示 Libra Rust bridge 的入站依赖；它由 Libra 的 `LB-01`/`LB-07`
  产出，Rust bridge 是 protocol/schema、method allowlist、error code、limits 和
  capability 的唯一权威。TypeScript 不创建第二份规范，只保存带 revision/SHA 的接收
  fixture 并从中生成类型或执行 runtime validation。
- `DEP-DSH-01` 表示固定的 DeepSeek Harness 上游 revision；它不改变 Libra bridge
  的协议权威，也不允许插件随意升级上游。
- 跨仓库发布顺序是 `REL-LB-01 → REL-TS-01`：先发布可验证的 Rust bridge protocol
  fixture，再发布消费该 fixture 的 TypeScript bundle。两边的 release evidence 必须
  记录 protocol revision、fixture SHA、package version 和 Harness revision；不存在
  Rust release 等待 TypeScript release、或 TypeScript release 自行先定义 server schema
  的循环依赖。

v1 两端必须逐项使用同一份 contract fixture：单 frame ≤ 256 KiB、单连接 in-flight request
≤ 64、event batch ≤ 64 events 且 ≤ 256 KiB、单 event ≤ 256 KiB、单 result ≤ 256 KiB、
request deadline 默认 30 秒、history/checkpoint page ≤ 100。事件 ack 表示 Libra 的
redacted projection 已 durable，不表示 Harness 原始 transcript 已迁移。标准方法名为：
`initialize`、`session.open`、`event.append`、`session.flush`、`session.close`、
`evidence.append`、`provenance.append`、`context.get`、`status.get`、`diff.get`、
`history.search`、`checkpoint.create`、`checkpoint.list`、`checkpoint.show`、
`checkpoint.restore`、`commit.create`、`review.run`、`workspace.claim`、
`workspace.renew`、`workspace.release`。未知 major、未知 method、scope/actor/lease
冲突和 redaction 不确定都 fail-closed；TypeScript outbox 只负责 Harness 侧恢复，
`agent_bridge_*` 表和 Libra transaction 才是服务端 durable projection 的归属。

## 已决议设计决策

### ADR-DHP-01: TypeScript 插件与 Libra Rust bridge 分仓

- **Status:** Accepted
- **Context:** DSH 插件依赖 Cordis、pnpm、profile/bundle 和 Harness 生命周期；Libra bridge 依赖 Rust runtime、SQLite、对象库和 workspace lease。
- **Decision:** 本仓库只维护 `@libra/dsh-bundle` 及其 TypeScript packages；Rust bridge 和 Libra storage 继续在 Libra 仓库实现。
- **Alternatives considered:** 把 TypeScript 代码放入 Libra `web/` 或 Rust crate；拒绝，因为会混淆发布生命周期、绕过 DSH loader，并扩大依赖面。
- **Consequences:** 需要 `DEP-LB-01` 协议依赖和双端 contract test；可以独立发布和回滚插件。
- **Revisit when:** Libra 与 Harness 形成统一 monorepo 或上游决定接纳该插件时。

### ADR-DHP-02: 统一 JSON-RPC NDJSON bridge

- **Status:** Accepted
- **Context:** Harness 需要同时写入低频工具结果和高频 session events；两套传输会产生不同的鉴权、错误和重试语义。
- **Decision:** 所有入站写入和高层查询均通过 `libra agent bridge --stdio`；stdout 只输出 JSON-RPC NDJSON，日志写 stderr/Harness logger。
- **Alternatives considered:** 直接访问 `.libra/libra.db`、shell 调用 CLI、保留旧工具服务器传输；均拒绝，因为无法统一权限、schema、幂等和审计。
- **Consequences:** Rust bridge 必须提供长连接、请求 ID、版本协商、batch ack 和稳定错误码。
- **Revisit when:** 需要远程多租户连接或 stdio 不再满足部署隔离时。

### ADR-DHP-03: 单 bundle、内部 package 边界

- **Status:** Accepted
- **Context:** 设计逻辑上包含 tools/session/workspace/context/UI，但目标仓库从空工作树开始，立即拆成多个独立 npm 发布物会放大版本和协议协调成本。
- **Decision:** 初期使用一个 `@libra/dsh-bundle` 对外发布，内部以 `packages/protocol`、`packages/bridge-client`、`packages/session`、`packages/tools`、`packages/workspace`、`packages/context`、`packages/ui` 分层；`packages/protocol` 只消费 `DEP-LB-01` 的 authoritative fixture，不成为第二个 schema source。
- **Alternatives considered:** 一开始发布 6 个 npm 包；拒绝，直到 bridge schema 和生命周期稳定前不增加发布面。
- **Consequences:** package 内部仍需保持单向依赖，稳定后可按实际复用度拆包。
- **Revisit when:** 至少有两个独立 DSH profile 或外部消费者需要复用子包。

## 全局工程约束

- **GC-01 现状核实前置:** 每张卡开工前刷新目标仓库、Libra bridge 依赖和固定 Harness revision 的事实锚点。
- **GC-02 单一事实源:** Libra bridge 发布的 versioned schema/contract fixture 是 JSON schema、协议版本、错误码、method/capability、limits 和 retryability 的唯一权威；TypeScript types 从接收 fixture 生成或由其校验，事件映射和 redaction adapter 也不得定义与 Rust contract 冲突的第二套语义。
- **GC-03 bridge-only:** 插件不得读取 `.libra/`、拼接 shell 命令或自行实现 Libra 存储协议。
- **GC-04 输出与错误契约:** stdout 只输出 JSON-RPC frame；stderr 可以写诊断但不得写 secret；错误必须包含稳定 code、request id 和 retryability。
- **GC-05 版本锁定:** 默认只支持 `dsh-v0.1.0-rc.7` 基线；Harness API 升级必须更新 revision、compat matrix 和 migration note。
- **GC-06 安全默认值:** handshake、repository/workspace identity、actor、approval、path 和 symlink 校验任一失败即 fail-closed。
- **GC-07 隐私:** 原始 prompt、reasoning、环境变量和敏感文件内容默认不写入；redaction 失败不得回退原文。
- **GC-08 原子性与恢复:** outbox 写入、batch ack、checkpoint/evidence association 和 lease 更新必须定义崩溃窗口与恢复动作。
- **GC-09 并发与资源:** child process、stdin/stdout、timer、queue、outbox、session listener 和 workspace lease 必须在 close/dispose 时释放。
- **GC-10 性能预算:** 不得每个 token/event spawn 子进程；batch、queue、payload、并发 session 和重试次数必须有上限。
- **GC-11 TypeScript 质量:** 开启 strict typecheck；生产代码不得引入未解释的 `any`、空 catch、未处理 Promise rejection 或静默 fallback。
- **GC-12 发布边界:** package exports、协议 schema、README、CHANGELOG 和 lockfile 必须在同一发布切片同步。

## 执行检查必备需求（强制）

- **ER-01 开工前安全检查:** 在目标仓库运行 `libra status --short --branch`，确认当前分支、脏状态和目标文件；不得覆盖既有用户改动。
- **ER-02 先核对后实现:** 刷新 `DEP-LB-01` 协议 fixture、`DEP-DSH-01` Harness revision、package API 和测试 target；不按过期行号实现。
- **ER-03 粒度门禁:** 开工前检查每张卡的 `Granularity`，发现新增行为轴、协议面或写集冲突时先拆卡。
- **ER-04 每卡验收门:** 每张卡必须通过 focused tests、lint/typecheck、文档/兼容同步和适用的 package build；计划完成前还要通过全量门。
- **ER-05 Review 门:** 每张实现卡必须有一次只读 Codex/Claude review；最终计划 review 必须为 `PASS`。
- **ER-06 文档收口:** 公开 package、bridge method、config 或错误码变化必须同步 README、protocol docs、CHANGELOG 和 compatibility matrix。
- **ER-07 签名/发布:** N/A，当前计划不发布 Libra Rust artifact；npm 发布由 `TS-06`/release owner 执行并保留 provenance。
- **ER-08 版本一致性:** package version、lockfile、bundle manifest 和 CHANGELOG 必须一致；发布前执行 `pnpm pack --dry-run`。
- **ER-09 外部依赖门:** `DEP-LB-01` 未提供版本化 schema、可运行 fixture 和错误码表时，真实 bridge 集成卡不得标记完成。
- **ER-10 越界故障:** 发现 bridge schema、Rust 存储或 Harness 上游行为超出本计划，任务置为 `blocked`，登记 `FIX-*` 或 `DEP-*`，不得静默扩张。
- **ER-11 远端后置门:** npm registry、真实 Harness profile 或真实 Libra binary 无法本地运行时，记录 `remote-pending` 证据，不得宣称 complete。
- **ER-12 发布串行:** npm package 发布、tag 和 release note 由唯一发布者串行执行；实现阶段可并行但 I–I 写集不得相交。

### 故障恢复矩阵

| 故障点 | 可接受残留 | 恢复动作 | 禁止结果 |
|---|---|---|---|
| child process 启动后 handshake 失败 | capped stderr、client error state、未发送请求 | kill/reap child，等待 backoff 或用户重试 | 把错误当成成功或无限重启 |
| batch 已发送、ack 未返回 | outbox batch 和 operation id | 保留 batch，重连后按 `(session_id,event_seq)` 重试 | 重试产生重复 checkpoint/evidence |
| redaction 失败 | 原始内容不落盘，仅保留错误摘要 | 标记 event rejected，要求显式重试/诊断 | 原文回退写入 |
| workspace lease 过期 | client-side stale handle | release handle，重新 claim 并校验 fence | 静默继续写入旧 workspace |
| profile install 中断 | 临时 pnpm/manifest 状态 | 恢复 package manifest/lockfile，再次安装 | 半完成 profile 被认为可用 |
